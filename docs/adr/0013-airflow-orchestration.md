# ADR-0013: Airflow orchestration of the batch chain (Phase 5)

- Status: Accepted for implementation (Phase 5).
- Context: Phase 4 jobs are idempotent CLIs that read the completed ledger of their upstream
  stage by pinned snapshot and skip identical work (ADR-0007…0011,
  [Phase 5 handoff](../phase5-handoff.md)). Phase 5 schedules them locally with Airflow
  (plan §Phase 5, flows O1/O3/O5) without changing their contracts, versions or ports.

## 1. Runtime

- Apache Airflow 3.3.2 on `apache/airflow:3.3.2-python3.11` (ADR-0001), profile `orch`,
  compose file `docker/compose.orchestration.yml`, UI/API on `127.0.0.1:8081` (container 8080).
- `airflow standalone` (API server, scheduler, DAG processor, triggerer) with LocalExecutor,
  `parallelism=1` (AGENTS.md §4, `AIRFLOW_PARALLELISM`), metadata in PostgreSQL database
  `airflow` as role `airflow` (ADR-0004). Standalone is a local/dev mode; it is acceptable here
  because the stack is single-user and loopback-only.
- Auth: simple auth manager (dev/test only per Airflow docs) with one `admin` user whose
  password is generated by `make env-orch` into `.env` and written to the passwords file at
  start-up. Fernet and API/JWT secret keys are generated the same way, never rotated silently.
- One-shot `airflow-init` service (idempotent): `airflow db migrate`, pool `spark_driver`
  (1 slot). A second run changes nothing.

## 2. How tasks run Spark

- The Airflow container is the Spark driver in client mode (`spark://spark-master:7077`).
  Its image adds Java 17, PySpark 3.5.5 and copies `/opt/spark/jars` additions (Iceberg runtime,
  Iceberg AWS bundle, PostgreSQL JDBC) from the pinned Spark image, plus `spark/` and `sql/`
  under `/app` — the same code and jars the `spark-submit` service uses.
- `spark.driver.host` comes from `SPARK_DRIVER_HOST` (default `omnichannel-spark-driver`,
  Airflow sets its own service name). Executors connect back over the compose network.
- The container mounts the same volumes as the `spark-submit` service: `lakehouse-config`
  (`/runtime`, ledgers) and `bronze-staging` (`/staging`), and receives the same job
  environment (catalog, S3, JDBC, PII key) from `.env`.
- It runs as root, like the existing `spark-submit` service, because ledgers and staging
  files in those volumes are owned by root. A non-root migration needs a separate ownership
  plan for existing volume contents and is out of scope.
- Rejected: mounting `docker.sock` to call `docker compose run` (root-equivalent host access);
  Spark cluster deploy mode (not supported for Python on standalone); a Spark provider
  operator (adds dependencies, hides the exact command). Tasks use `BashOperator` with an
  explicit `spark-submit` command.

## 3. One driver at a time

- Every Spark task is in pool `spark_driver` (1 slot) and `parallelism=1`.
- Every Spark submission, from Airflow or `make`, is wrapped by
  `python -m spark.lib.driver_lock`, which takes an exclusive `flock` on
  `/runtime/locks/spark-driver.lock`. A manual `make` call fails fast with exit code 75
  (`spark_driver_busy`); Airflow tasks wait up to 300 s (`--wait`) for a manual job to finish,
  then exit 75 and use their normal retry. A crashed holder releases the lock automatically.

## 4. DAG topology and dates

- One DAG per job, named like the job (AGENTS.md §6), `schedule=None`, `max_active_runs=1`:
  `dp1_bronze`, `dp2_silver`, `dp2_gold`, `dp3_features`, `dp3_return_labels`, `dp4_warehouse`.
  Each can be triggered alone with `dataset_run_id` (param, regex `[0-9a-f]{20}`) and a
  logical date.
- Controller `batch_daily` (`@daily`, `start_date=2026-01-01`, `end_date=2026-01-03` for the
  demo data, `catchup=False`) triggers them in order for its own logical date with
  `TriggerDagRunOperator(wait_for_completion=True, deferrable=True, reset_dag_run=True)`.
  Deferral frees the only executor slot while waiting, so `parallelism=1` cannot deadlock.
  Backfills use `airflow backfill create` on `batch_daily`.
- Date mapping (`ds` = logical date, UTC):

| DAG | Tasks | Arguments |
|---|---|---|
| `dp1_bronze` | wait for `s3://raw/manifests/<run>/stream_manifest.json`; JSONL for 5 channels; Walmart JDBC | `--run-id R --run-date ds --channel C [--source jdbc] --mode incremental` |
| `dp2_silver` | 5 channels | `--run-id R --run-date ds --channel C --mode incremental --fail-on-reject` |
| `dp2_gold` | publish, verify | `--run-id R --mode full`; `--verify` |
| `dp3_features` | publish, verify | `--run-id R --as-of-date ds --mode incremental`; `--verify` |
| `dp3_return_labels` | publish, verify | `--run-id R --as-of-date ds --horizon-days 14 --mode incremental`; `--verify` |
| `dp4_warehouse` | export, verify | `--run-id R --run-date ds --mode full --no-regress`; `--verify --run-id R` |

- `incremental` Bronze/Silver skip completed identical slices (JDBC by snapshot content,
  ADR-0007); Gold skips when the Silver publication and policy are unchanged.
- DP3 runs **incremental** for one date: `full` means "the requested dates are the whole run"
  and would delete every other date of the run. Incremental replaces only `ds` and skips when
  that date's provenance (Gold publication, policy, horizon) is current.
- The warehouse mirrors the latest 30-day window. With `--no-regress`, a date older than the
  committed export for the same Gold publication is skipped, so a backfill of history never
  moves the window backwards; the newest date's run exports it.
- A rerun of the same dates therefore publishes nothing new (checked by `make e2e`).

## 5. Task contract

- Exit code ≠ 0 fails the task; a job that reports `skipped: true` succeeds.
- The task command prints the job output to the task log and, as its last line, the last
  allowlisted event (`docker/batch/ci_events.py`), which becomes the task's XCom; raw lines
  are never parsed into XCom.
- Defaults: owner `data-platform`, `retries=1`, `retry_delay=2 min`, tags, pool, and
  `execution_timeout` per task from measured durations (warehouse 45 min, Gold 20 min,
  others 15 min, verify 10 min, manifest sensor 30 min in reschedule mode).
- `on_failure_callback` writes one structured log line (DAG, task, run, try); an optional
  webhook URL (`AIRFLOW_ALERT_WEBHOOK_URL`) is off by default. Airflow 3 has no 2.x-style SLA;
  timeouts bound runtime instead.
- DAG files do no I/O at import time and never use `datetime.now()`.

## 6. Testing

- `make test-dags` runs `airflow/tests` with pytest inside the Airflow image: DagBag import
  errors, cycles, defaults (owner, tags, retries, `max_active_runs=1`, pool, timeout),
  rendered commands for a sample date, param validation.
- `make test` skips Airflow tests when Airflow is not installed in `.venv`.
- `make e2e` runs `batch_daily` end to end through Airflow on a dedicated small dataset and
  asserts ledgers and verifiers; reruns must skip.

## 7. Consequences

- The Airflow container holds the same credentials as the `spark-submit` service; secrets
  stay in `.env`, the UI is loopback-only, and task output passes through the event allowlist.
- Resource budget: Airflow `mem_limit` 3 GiB (standalone + one driver JVM); with core + batch
  limits (~7.5 GiB) the total stays within the ~11.7 GiB host. Other profiles stay off.
- Layer assets on the last publish/verify task give data-aware visibility in the UI only;
  `maintenance_iceberg` is a weekly dry-run report (ADR-0014), paused at creation.
- Lineage to DataHub (O4), CDC DAG and Iceberg maintenance with real deletion are later work.
